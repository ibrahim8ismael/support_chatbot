# Chatwoot Integration

Chatwoot owns customer channels. This app connects as an Agent Bot: Chatwoot
sends events to the API, and the API queues work before optionally posting a
reply back to Chatwoot.

## Status and scope

The repository implements webhook intake, HMAC verification when configured,
queue-backed processing, conversation/message persistence, inbox-to-KB
bindings, model answers, Chatwoot replies, escalation notes, and pause/resume
controls. The integration has **not** been validated against the user's live
Chatwoot instance in this workspace. Validate a test inbox with the exact
Chatwoot version before routing production traffic.

This app processes events delivered after the Agent Bot is connected. It does
not import or backfill historical conversations/messages from Chatwoot. The
dashboard's conversation explorer therefore starts showing conversations after
the first processed webhook for each conversation.

## Credentials and environment

Copy the keys into the API's environment file (for Docker production, the
repo-root `.env`; for local development, `apps/api/.env.local`). Keep actual
credentials out of committed files.

| Variable | Purpose | Required when |
| --- | --- | --- |
| `CHATWOOT_BASE_URL` | Chatwoot origin, without an account/API path | Connecting to Chatwoot |
| `CHATWOOT_ACCOUNT_ID` | Numeric account id from Chatwoot URLs | Connecting to Chatwoot |
| `CHATWOOT_BOT_TOKEN` | Agent Bot API token used to post replies, notes, and labels | Sending replies or managing labels |
| `CHATWOOT_WEBHOOK_SECRET` | Long random path segment used in this app's webhook URL | Receiving webhooks |
| `CHATWOOT_WEBHOOK_SIGNING_SECRET` | Signing secret Chatwoot gives the Agent Bot; verifies signed requests | Chatwoot v4.13+ signed Agent Bot webhooks |
| `CHATWOOT_ACCOUNT_API_TOKEN` | User API token used only by the dashboard's inbox discovery endpoint | Optional inbox-name discovery |

`CHATWOOT_WEBHOOK_SIGNING_SECRET` and `CHATWOOT_WEBHOOK_SECRET` are different
secrets. The first comes from Chatwoot and validates its signature. The second
is generated by us and appears in the callback URL. The Agent Bot token is a
third credential used for outbound API calls. The account API token is optional
and should be a user token with inbox-list access; it is not needed to send
replies.

Generate the URL-path secret with `openssl rand -hex 32`. Configure the Agent
Bot callback URL as:

```text
https://<api-host>/api/webhooks/chatwoot/<CHATWOOT_WEBHOOK_SECRET>
```

For local development, use a reachable tunnel URL rather than `localhost` in
Chatwoot. Copy Chatwoot's Agent Bot signing secret exactly into
`CHATWOOT_WEBHOOK_SIGNING_SECRET`. Restart/recreate the API container after
changing environment values.

## Setup

1. Create an Agent Bot in Chatwoot and set its callback URL to the URL above.
2. Copy the bot API token to `CHATWOOT_BOT_TOKEN` and, for Chatwoot v4.13+,
   copy its signing secret to `CHATWOOT_WEBHOOK_SIGNING_SECRET`.
3. Configure the base URL and account id, then restart the API.
4. Bind the Agent Bot to a **test inbox** in Chatwoot.
5. In this app, map that inbox to one or more knowledge bases. Inbox discovery
   in the dashboard additionally needs `CHATWOOT_ACCOUNT_API_TOKEN`; otherwise
   enter the numeric inbox id manually.
6. Confirm the global `bot_enabled` setting is on and the inbox binding is
   enabled with at least one knowledge base. The global switch defaults to off.
7. Send a test message and confirm the event, reply, and any handoff in both
   Chatwoot and the app's conversation explorer before expanding rollout.

## Webhook handling

Endpoint: `POST /api/webhooks/chatwoot/:secret`. It is a public endpoint, so
the URL secret is always checked. If `CHATWOOT_WEBHOOK_SIGNING_SECRET` is set,
the handler also requires valid `X-Chatwoot-Signature` and
`X-Chatwoot-Timestamp` headers. It verifies HMAC-SHA256 over
`{timestamp}.{raw request body}` and rejects timestamps more than five minutes
from server time. A signature without a configured signing secret is rejected;
unsigned requests are accepted only when no signing key is configured, for
older Chatwoot versions.

The handler acknowledges supported events after enqueueing them to BullMQ. It
returns 200 for unsupported events and malformed `conversation_updated` events,
400 for malformed `message_created` payloads, 401 for invalid signatures, 404
for a wrong path secret, and 500 if it cannot enqueue. The worker performs
Chatwoot calls and model work outside the webhook request. Queue jobs use
retry/backoff; completed and failed jobs remain inspectable for the configured
retention windows.

Supported event behavior:

| Event | Behavior |
| --- | --- |
| `message_created` | Process only incoming, non-private messages from a contact. Ignore events outside the configured account, messages without required conversation/contact/inbox ids, and outgoing/system messages. |
| `conversation_updated` | Synchronize pause, escalation, and human-assignee state for a conversation already stored by this app. |
| Other events | Acknowledge and ignore. |

For an incoming message, the worker checks that the inbox is enabled and has
knowledge bases, checks the global kill switch, and stops when a human is
assigned or the conversation has `ai-paused` / `ai-escalated`. Text messages go
through retrieval and the existing grounded answer flow. Non-text messages,
messages with attachments, empty messages, and explicit requests for a human
are escalated; escalation adds `ai-escalated`,
posts an internal note, and sends a customer-facing fallback. Outgoing messages
are filtered from the inbound path to avoid reply loops.

The database deduplicates local message rows by Chatwoot message id. Jobs are
serialized with a per-conversation Redis lock, and completed answer events are
used to avoid replying again to a retried webhook. Chatwoot's message-create
endpoint does not provide an atomic transaction with our database, so a process
crash after Chatwoot accepted a reply but before the reply was saved locally can
still leave an uncertain delivery and needs operator review.

## Chatwoot API calls

All outbound calls are owned by `ChatwootService`, use the account-scoped API
path, and have a 10-second timeout. The Agent Bot token is used for sending
messages and managing conversation labels. Inbox listing uses a separate
user-level account API token because the Bot token cannot access that account
endpoint. API failures escape the worker so BullMQ can retry the job; the
dashboard inbox-list endpoint reports unavailable when discovery is not
configured.

The app posts public replies and private notes through
`POST /api/v1/accounts/{account_id}/conversations/{conversation_id}/messages`.
It reads the existing conversation labels before updating them because
Chatwoot's label endpoint replaces the full label list.

## Validation and limitations

- No historical conversation/message backfill is implemented. Existing old
  messages in Chatwoot are not copied when the Agent Bot is connected.
- No live Chatwoot request was made during this code change. Verify callback
  reachability, signing, token permissions, message posting, and label behavior
  against the deployed self-hosted Chatwoot version.
- The `conversation_updated` payload and signed webhook behavior can vary by
  Chatwoot version; compare one anonymized event from the test instance with
  `apps/api/src/modules/chatwoot/chatwoot-webhook.ts` before enabling traffic.
- A human reply without assigning the conversation or adding `ai-paused` is not
  detected as a takeover yet; use an assignee or the pause control.
- A separate history-import feature would be required to load older messages
  for context or to populate historical conversations in the dashboard.
